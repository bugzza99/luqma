Phase 0 — تثبيت خط الأساس وتأمين العمل
الهدف: نضمن أن أي مشكلة جديدة ظهرت بسبب الإصلاح يمكن اكتشافها فورًا.
المهام:
إنشاء CI يشغّل:
Analyze
Unit/Widget tests
PGlite
Supabase stack
Edge Function tests
Release build
فحص الأسرار داخل APK
عزل بيانات الاختبارات الحية وتنظيفها بعد كل run.
رفع مهلة الاختبارات الشبكية وتصنيف أخطاء الشبكة عن الأخطاء الوظيفية.
إضافة smoke tests لأهم التدفقات الحالية قبل تعديلها.
أخذ snapshot لإعدادات الإنتاج الحالية.
إيقاف/إخفاء مؤقتًا:
Marketing Push المدفوع.
OTP.
الدفع الإلكتروني.
AdMob.
أي feature flag لا يملك تنفيذًا فعليًا.
عدم تغيير min_supported_version حاليًا.
بوابة الخروج:
CI ثابت ينجح مرتين متتاليتين.
لا توجد تغييرات غير موثقة في الإنتاج.
الميزات غير المكتملة لا تظهر كمزايا عاملة.
Phase 1 — إصلاح العقود والإعدادات بطريقة متوافقة
الهدف: تجهيز Backend جديد تقبله النسخ القديمة والجديدة معًا.
1. إصلاح support_whatsapp
الترتيب الآمن:
إضافة support_whatsapp مع قيمة صحيحة.
إبقاء supportWhatsapp مؤقتًا.
جعل القراءة تقبل المفتاح الجديد ثم القديم كـfallback.
تحديث seed والإدارة ليكتبا المفتاح الجديد.
بعد انتشار النسخة الجديدة، إزالة القديم في migration مستقلة.
2. فصل إعدادات الإصدارات
بدل min_supported_version العام:
customer_min_supported_version
merchant_min_supported_version
admin_min_supported_version
رابط تحديث مستقل لكل تطبيق.
مهم جدًا: لا يتم حذف المفتاح القديم مباشرة؛ التطبيقات الجديدة تقرأ المفتاح الخاص بها ثم تستخدم القديم كـfallback.
3. Server-side config validation
تعريف نطاق كل قيمة في الخادم.
رفض القيم السالبة أو غير المنطقية داخل RPC.
إعادة القيم المحفوظة فعليًا إلى Admin App.
توحيد قواعد التحقق بين الخادم وDart.
بوابة الخروج:
النسخ القديمة ما زالت تعمل.
النسخ الجديدة تقرأ الإعدادات الجديدة.
القيم غير الصحيحة تُرفض بدل تخزينها ثم تجاهلها.
Phase 2 — حماية البيانات والعمليات الحساسة
هذه المرحلة تسبق إصلاح الواجهات لأن الواجهة لا تستطيع حماية البيانات وحدها.
1. Idempotency للطلبات
الترتيب:
إضافة client_order_id nullable.
إضافة unique constraint على (customer_uid, client_order_id) عندما لا تكون القيمة null.
تحديث place_order ليستقبل المعرف اختياريًا؛ النسخ القديمة تستمر في العمل.
جعل RPC يعيد الطلب الموجود عند تكرار نفس المعرف.
تحديث Customer App لإنتاج UUID ثابت لكل checkout.
بعد انتشار النسخة الجديدة يمكن جعل المعرف إلزاميًا لاحقًا.
اختبار القبول الأساسي:
الخادم ينشئ الطلب، الرد يضيع، العميل يعيد المحاولة؛ يجب أن يبقى طلب واحد فقط.
2. إعادة تصميم Push Tokens
الترتيب الآمن:
إنشاء جدول device_tokens مستقل.
إضافة RPC ذرية لتسجيل token ونقل ملكيته.
جعل send-push يقرأ من الجدول الجديد والمصفوفة القديمة مؤقتًا.
تحديث التطبيقات لاستخدام RPC الجديدة.
نقل tokens القديمة وإزالة التكرار.
بعد انتشار التطبيقات، إيقاف القراءة من users.fcm_tokens.
حذف العمود القديم في إصدار لاحق، وليس في نفس المرحلة.
3. تعطيل الموظفين وسحب الجلسات
إنشاء Admin RPC أو Edge Function بدل update المباشر.
تغيير is_active.
سحب sessions/refresh tokens.
فحص staff.is_active مباشرة في العمليات الحساسة.
عدم الاعتماد على JWT claims القديمة وحدها.
4. Push outbox lease
إضافة claimed_at وclaim_token.
منع عاملين من معالجة الرسالة نفسها.
انتهاء صلاحية الـlease لاستعادة الرسائل المتوقفة.
جعل التسوية مرتبطة بنفس claim_token.
إضافة idempotency لكل recipient.
بوابة الخروج:
لا يتكرر طلب عند فقد الرد.
لا تبقى إشعارات الحساب السابق على جهاز مشترك.
الموظف المعطل يفقد الصلاحية فورًا.
تشغيل عاملَي push بالتزامن لا يكرر الرسائل.
Phase 3 — توحيد أوامر التطبيق ومعالجة الأخطاء
الهدف: إنهاء رسائل النجاح الكاذبة وتوحيد سلوك الـfake مع الإنتاج.
المهام:
كل عملية تعديل ترجع:
الصف المعدل، أو
عدد الصفوف المتأثرة، أو
Failure واضحة.
منع Ok عند تعديل صفر صفوف.
إنشاء Action/Command layer موحدة للعمليات.
كل زر حساس يملك:
Loading state.
منع الضغط المكرر.
رسالة نجاح بعد نجاح مؤكد.
رسالة خطأ مناسبة.
Retry إن كان آمنًا.
إصلاح:
إلغاء الطلب.
إرسال الشكوى.
اعتماد/رفض الإعلان.
تعطيل الموظف.
اعتماد الوسائط.
تغيير حالة التاجر.
إغلاق الشكاوى.
حفظ الفوترة.
كتابة Repository contract tests تُشغّل على Fake والتنفيذ الحقيقي.
في نفس المرحلة:
حفظ اسم الموظف في جدول staff.
جعل إنشاء الموظف وعملية audit ذرية قدر الإمكان.
فحص فشل حذف Auth user عند حدوث partial failure.
حسم هل مالك المتجر مسموح له بإنشاء مندوبيه أم أن الميزة خارج نطاق الإصدار.
بوابة الخروج:
لا تظهر رسالة نجاح عند فشل الخادم.
الـfake وSupabase يرجعان نفس أنواع النتائج.
كل عملية إدارية حساسة تنتج Audit Log واحدًا.
Phase 4 — إصلاح Offline Queue للمندوب
نفعلها بعد تثبيت الهوية والأوامر حتى لا نبنيها فوق Push/Auth غير مستقر.
المهام:
إضافة schemaVersion لكل سجل.
تضمين ownerUid.
تخزين queue تحت مفتاح متعلق بالمستخدم.
رفض النوع غير المعروف بدل تحويله إلى delivered.
نقل queue القديمة بحذر:
إذا أمكن إثبات مالكها تُنقل.
وإلا تُعزل وتظهر للمستخدم للمراجعة.
عدم حذف العملية المرفوضة صامتًا.
إظهار قائمة عمليات معلقة/فاشلة للمندوب.
منع flush إذا كان المستخدم الحالي غير مالك السجل.
بوابة الخروج:
عمليات المندوب A لا ينفذها المندوب B.
JSON فاسد لا يتحول إلى عملية تسليم.
قتل التطبيق أثناء الحفظ أو الإرسال لا يفقد العملية.
Phase 5 — إصلاح تجربة الإشعارات والتحديث
1. Notification deep links
Navigation dispatcher مركزي لكل تطبيق.
دعم:
التطبيق مغلق.
التطبيق في الخلفية.
التطبيق مفتوح.
التحقق من صلاحية orderId.
منع تنفيذ نفس tap مرتين.
فتح الشاشة الصحيحة حسب دور المستخدم.
2. Android notification onboarding
شرح سبب الإذن قبل طلبه.
التعامل مع الرفض و“عدم السؤال مرة أخرى”.
فحص canUseFullScreenIntent.
fallback إلى إشعار عادي.
مراجعة ضرورة REQUEST_IGNORE_BATTERY_OPTIMIZATIONS.
شاشة “حالة الإشعارات” داخل تطبيق التاجر.
3. Force Update
تطبيق الإعدادات المنفصلة من Phase 1.
رابط Play صحيح للعميل والتاجر.
رابط APK صحيح للإدارة.
مسار طوارئ يسمح بإصلاح إعداد خاطئ.
عدم رفع الحد الأدنى إلا بعد التأكد من توفر الإصدار الجديد فعليًا.
بوابة الخروج:
الضغط على الإشعار يفتح الطلب الصحيح في الحالات الثلاث.
رفض الإذن لا يكسر التطبيق.
تطبيق الإدارة لا يمكن أن يقفل نفسه على رابط غير موجود.
Phase 6 — إكمال التسويق المدفوع
تأتي متأخرة عمدًا لأنها تعتمد على Push Tokens وOutbox وResult handling وAudit.
المهام:
إنشاء sendPromotionPush خادمية.
تطبيق الحصة الأسبوعية داخل transaction.
إضافة marketing preference للعملاء.
استثناء من أوقف التسويق.
idempotency لكل حملة ومستلم.
تسجيل:
عدد المستلمين.
نجاح FCM.
الفشل الدائم.
الفشل القابل لإعادة المحاولة.
عدم احتساب الحملة كمرسلة بمجرد اعتمادها.
عرض حالة واضحة:
Approved.
Scheduled.
Sending.
Sent.
Partially failed.
Failed.
بوابة الخروج:
اعتماد الحملة وحده لا يستهلك الحصة.
الحصة تُستهلك عند queue ناجحة.
لا يستلم العميل الرافض للتسويق.
لا يستلم العميل نفس الحملة مرتين.
Phase 7 — الخصوصية واستعادة الحساب
يمكن إعداد الوثائق مبكرًا، لكن اعتمادها النهائي يجب أن يكون بعد استقرار نموذج البيانات.

Data inventory.

رابط عام للسياسة.
حذف حساب من التطبيق ومن الويب.
تعريف retention policy.
حذف/تجهيل:
العناوين.
FCM tokens.
البيانات الشخصية.
Sentry identifiers.
الاحتفاظ فقط بالسجلات المالية الضرورية بعد تجهيلها.
إضافة مسار “نسيت كلمة المرور”.

حماية reset password:
rate limiting.
audit إجباري.
session revocation.
إجبار تغيير كلمة المرور المؤقتة.
بوابة الخروج:
اختبار حذف حساب كامل.
المستخدم يستطيع استعادة حسابه دون مسار يدوي غامض.
سياسة الخصوصية مطابقة للسلوك الحقيقي، وليست نصًا عامًا.
Phase 8 — إعادة الهيكلة وSOLID
لا أنصح بعمل refactor واسع قبل إصلاح السلوك؛ وإلا سنغيّر الهيكل والمنطق في الوقت نفسه ويصعب معرفة مصدر الأعطال.
بعد استقرار السلوك:
تقسيم الشاشات التي تتجاوز 600–800 سطر.
تقسيم providers.dart حسب المجال.
فصل:
Form state.
Validation.
Commands.
Presentation.
إنشاء Use Cases للعمليات الحساسة.
تقليل اعتماد الواجهات على المستودعات مباشرة.
توحيد مصادر الحقيقة بين الوثائق والكود والمخطط.
تحديث وثائق Firebase القديمة إلى Supabase.
تثبيت إصدارات Edge Function imports وإضافة lock file.
ترقية التبعيات على دفعات صغيرة، لا دفعة واحدة.
بوابة الخروج:
كل refactor يمر على نفس contract tests.
لا تغيير سلوكي غير مقصود.
كل ملف رئيسي له مسؤولية واضحة.
